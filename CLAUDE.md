## Key technical findings from recent work (don't re-discover these)

- **Vivino's `www.vivino.com/api/explore/explore` search API silently ignores the `q` param** for unauthenticated requests — returns the same generic "trending wines" list regardless of query (verified live, repeatedly). `search_wine()` in `vivino.py` now checks the top result for basic relevance before trusting it, falling back to HTML scraping (which *does* do real text search) when it looks wrong.
- **`api.vivino.com` (the mobile-app-facing backend) is open and unprotected** — no auth, no special headers, plain `GET https://api.vivino.com/wines/{id}` / `/vintages/{id}` / `/grapes/{id}` / `/foods` all work. Used for reliable refreshes once a wine's `vivino_id` is known (`VivinoClient.get_wine_by_id`). It has **no search endpoint** (by-id lookup only) and **no price data anywhere** — confirmed via extensive live testing (explore API, HTML scrape, real browser navigation, mobile API, even `curl` with browser-identical headers). Vivino's real price is not reliably scrapable; AI estimation (with user consent) is the fallback.
- A `Vivino Batch failed` bug turned out to be a websocket schema validation error (`ai_fallback` param sent by the frontend but not declared in the backend schema) — always check HA logs (`Paramètres > Système > Journaux`) for exact errors before guessing.
- LWIN / Liv-ex was investigated as a wine-ID/pricing source and **rejected**: the free LWIN database has no price/rating data (identification only), and Liv-ex's price data (Wine Matcher, Automation) is a professional fine-wine-trade product, not viable for this project.
- **Vivino's real cellar sync (reading/writing the user's own cellar) is possible via `www.vivino.com`'s Inertia.js endpoint using a pasted session cookie** — see `los7702`'s work above. Not yet in this repo.
- **iOS Safari blocks the live camera when the page is reached over `http://` (not a secure context) — confirmed on `dobunzli`'s own setup; worth checking whether this user's HA is also reached over plain http.** Not a secure context ⇒ Safari does not expose `navigator.mediaDevices` at all ⇒ `getUserMedia` throws a `TypeError`. No code fix exists; `label-camera.ts` detects it up front and offers the file input, which carries `capture="environment"` and opens the native camera with no secure context needed. If this doesn't reproduce for this user, it's because they're on https — good, nothing to do.
- **Camera errors must be told apart by `err.name`, never `err.message`.** Safari's denial message is "The request is not allowed by the user agent or the platform in the current context" — it contains neither "NotAllowed" nor "Permission", so substring matching on the message sends every iOS failure to the generic branch. Shared helpers live in `frontend-src/src/utils/camera.ts`.
- **Barcode scanning cannot work on iOS at all**: WebKit does not implement `BarcodeDetector`. Unrelated to the http/https question — even over https it reports "not supported on this browser". Unblocking it needs a WASM decoder (zxing) — ask this user whether that dependency is worth adding before spending time on it.
- **`hass.data["lovelace_resources"]` does not exist and never has** — that wrong key is why card auto-registration could silently do nothing, which is upstream issue #1 ("Custom element not found"). The collection is at `hass.data[LOVELACE_DATA]` (a `LovelaceData` dataclass, `.resources`) on current HA, or a plain `hass.data["lovelace"]` dict on older ones. Two traps around it: `async_items()` does **not** load the store (`ResourceStorageCollection` defers until a write), so an existence check reads empty and duplicates the resource on every restart — call `_async_ensure_loaded()` first; and YAML-mode dashboards have no `async_create_item` at all, so registration is impossible there by design.
- **Which add path calls what** (measured by `dobunzli` 2026-08-22, rebalanced in PR #29): barcode hit ⇒ Vivino only; barcode miss ⇒ falls through to the label; label photo ⇒ AI, *plus* a non-blocking Vivino lookup fired after the details step opens; search by name ⇒ Vivino only. Before #29 the label path never touched Vivino at all, so photo-added wines had no rating and **no `vivino_id`**, which also barred them from the cheap by-id refresh. The background enrichment only ever fills gaps and never overwrites the AI's reading, the user's photo, or name/winery/vintage — and it checks the candidate really is the same wine, because Vivino answers every query with something.
- **Vivino latency, measured by `dobunzli` with production headers**: the explore API takes 1.1–1.7 s and returns ~910 KB for five results; grape lookups are 0.06–0.2 s each. AI label recognition is a single call, no retry, 45 s timeout — that wait is entirely the AI provider's (check what this user's own provider/relay is if optimizing this path), so there is nothing to optimise on our side beyond not lengthening it. Requests that are independent now run concurrently (`search_wine`'s explore + HTML, `lookup_barcode`'s two barcode DBs, grape names). **`fetch_extras=False` must stay sequential** — that flag exists so batch refresh does not double its request volume across the whole cellar.
- **Occupancy and placement math is shared, not re-derived**: `frontend-src/src/utils/location.ts` owns the notion of a *container* (a bin, a box, the bottom zone, or one grid slot with its depth) plus usage, labels, next-free-depth and multi-bottle planning. `utils/suggest.ts` (where a new bottle should go) and `utils/arrange.ts` (what is untidy) both build on it. It previously existed in four diverging private copies.

## Deploy workflow (Synology, no CI)

- No CI/CD, no remote dev environment. After any change: list the exact changed `.py` files + compiled frontend JS to copy, user copies them via the Synology File Station, then does a **full Home Assistant restart** (a simple integration reload is NOT enough — Python module caching).
- Frontend: TypeScript/Lit in `frontend-src/src/`, built via `npm run build` (run from `frontend-src/`) to `custom_components/wine_cellar/frontend/wine-cellar-card.js`. After any frontend change, bump `FRONTEND_VERSION` in `custom_components/wine_cellar/const.py` (format `YYYYMMDD` + incrementing letter) to bust the browser cache.
- **HACS-based testing — the user's own instance tracks `dobunzli/ha-wine-cellar` directly via a HACS custom repository (not `origin`/JYves72, and not just Synology File Station copies).** Since `dobunzli` is a third party's fork, this is worth the user's own periodic re-confirmation — it means the live Home Assistant install auto-updates from a repo the user doesn't control. HACS's "update available" detection is driven by GitHub Releases, not raw commits on `main` — after merging a PR to `main` (on whichever repo is actually being tracked), bump `manifest.json`'s `version` (semver: patch for fixes, minor for features) and `gh release create vX.Y.Z --target main` on that commit, or HACS will keep resolving to the last-tagged release and silently miss the fix. Skip the version bump for no-op/doc-only changes (e.g. a LICENSE-only PR) unless asked otherwise. During the staged catch-up to `dobunzli` (see above), consider asking the user whether to cut a matching release at each checkpoint (v2.12.0, v2.13.0, v2.14.2) or batch them into one release at the end — either is fine, just ask rather than assuming.
- **After every deploy (Synology copy *or* HACS redownload) + full HA restart, also remind the user to hard-refresh the browser tab (Cmd+Shift+R).** Home Assistant's frontend is a persistent single-page app — restarting the backend does NOT reload an already-open tab's JS. Two consecutive "the fix still doesn't work" reports on this project turned out to be exactly this: the fix was correct both times, the browser tab just hadn't picked it up yet. Don't let "restart Home Assistant" alone imply the browser will pick up new code.
- Verification (no live HA access from here): `npm run build` (4 pre-existing `TS2339` warnings in `add-wine-dialog.ts` re: `BarcodeLookupResult` are known/harmless, ignore them), `node --check` on the compiled JS bundle, `python3 -c "import ast; ast.parse(...)"` per changed `.py` file (Windows: use `python`, not `python3` — the latter resolves to a Microsoft Store stub unless disabled under Settings > Apps > Advanced app settings > App execution aliases).
- **Local frontend preview**: `custom_components/wine_cellar/frontend/index.html` is a standalone preview page with a full mock `hass` object (mocked `callWS` for every command the card uses — wines, cabinets, buy list, history, settings, etc. — no real backend needed). `.claude/launch.json` defines `preview-server` (`python3 -m http.server 5051` in the frontend dir) which serves it directly against the last `npm run build`; `frontend-dev` (`npm run dev`, port 5050) is rollup watch only. **The preview caches hard: `location.reload()` will happily re-run the previous bundle.** Use `navigate` with `force: true` after a rebuild, and check something you just changed is actually present before concluding a fix does not work. Open it to interact with the *real* compiled component — including real mouse drag-and-drop — before asking the user to test on Synology/HACS. Includes a dedicated "Capacity Test" cabinet (a Bulk Bin already at capacity + a Spare Bin) for exercising the bin/box capacity-check logic specifically. Prefer this over writing a throwaway test harness from scratch. For a case the mock doesn't cover cleanly, a synthetic DOM `drop` event (with a hand-built `dataTransfer.getData("text/plain")` payload matching what `cabinet-grid.ts`'s real drag produces) is a reliable way to exercise `_onWineDrop` deterministically without fighting mouse-coordinate drag simulation.
- **A repo-local PreToolUse hook blocks `cat`/`head`/`tail`/`sed`/`awk` in Bash and the Read tool without `offset`/`limit` for files >150 lines.** Use `Read` with `offset`/`limit`, or plain `grep` (careful: piping `grep` into `head`/`tail` in the *same* command also trips the hook).
- **This repo may be checked out in more than one place** (confirmed 2026-08-25: an SSH-connected Home Assistant checkout, and a local Windows copy) — don't assume they stay in sync; re-check `git log --oneline -3 main` on whichever checkout you're using before relying on its state. A network-mapped drive (`Z:`) was also seen for this repo but couldn't be read reliably by tooling (stat failures) — prefer a local-disk checkout when one is available.

## Branch / PR workflow

One branch per feature/fix, tested by the user on Synology, then PR + merge on the fork. **Branch from `main`, not from wherever you happen to be standing** — starting a second feature without checking out `main` first silently stacks it on the previous unmerged branch (happened once; fixed with `git rebase --onto main <old-base> <branch>`, plus a bundle rebuild, since the compiled JS then contained code the branch's sources no longer had).

**Several branches open at once is a deploy problem, not just a review one**: each carries its own compiled bundle and its own `FRONTEND_VERSION`, and the user can only run one on the Synology. When they pile up, merge them and hand over a single rebuilt bundle from `main` rather than asking for several deploys. Resolve the inevitable `const.py` / bundle conflicts by **rebuilding**, never by taking one side — a bundle picked from one side no longer matches its sources. After pushing a merge commit, GitHub needs ~10–20s to recompute mergeability; `gh pr merge` fails with "not mergeable: the merge commit cannot be cleanly created" until it does. Wait and retry rather than believing it. For genuinely large sessions, group related changes into a small number of themed PRs rather than one-per-tiny-fix (discussed and agreed with the user) — but if PRs are stacked (PR B based on PR A's branch), **do not delete branch A when merging PR A** (`gh pr merge --delete-branch`) until PR B has been retargeted/merged — deleting a stacked PR's base branch auto-closes it on GitHub. Retarget or merge in the right order instead.
